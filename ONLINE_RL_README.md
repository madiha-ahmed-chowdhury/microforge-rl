## The Shift: Offline RL → Online RL

### What offline RL gave us

The offline phase collected 7000 transitions (500 problems × 14 fixed configs) and trained BC, CQL, and IQL on that frozen dataset. The agent studied historical data like a textbook. It never got to try anything itself.

Results were reasonable but limited by two things:
- The 14 configs were hand-designed. The agent could only pick from those 14 options, even if the optimal config sat between two of them.
- 28% of problems had wrong code — the agent could not learn anything from those because the failure was not a resource problem.

### What online RL adds

The agent learns by doing. Every microVM execution is a training step. The policy updates in real time after every run. Two fundamental improvements:

**Continuous action space** — instead of choosing from 14 fixed options, the agent outputs any CPU, memory, and timeout value. It can discover configs that the hand-designed set never included.

**Code refinement loop** — when the LLM generates wrong code, the system calls the LLM again with feedback and gets a fixed version. The RL agent handles resource failures. The LLM handles correctness failures. Each component is responsible for what it can fix.

## The Online RL Loop — Complete Flow

```
Task arrives (one of 500 EffiBench problems)
        ↓
Load from storage (already collected, no API call needed):
  stress_input    ← large test input generated by prep VM
  ref_output      ← oracle answer from canonical solution
  generated_code  ← LLM code from offline phase
  state           ← 19 feature state vector
        ↓
If stress_input not stored (old problems without it):
  Boot PREP VM once (500mc / 256MB)
  Run test_case_generator → stress_input
  Run canonical solution → ref_output
  Tear down prep VM
  Save to storage for future use
        ↓
Agent picks resource config (continuous, see below)
        ↓
Boot CONFIG VM with agent's chosen resources
Send code + stress_input via vsock
Collect: exit_code, wall_time_ms, cpu_user_ms,
         mem_peak_kb, stdout, timed_out
Tear down CONFIG VM
        ↓
Compare stdout to ref_output → tests_passed
        ↓
┌────────────────────────────────────────────────┐
│              What happened?                     │
│                                                 │
│  TIMEOUT    → resource failure                  │
│               agent bumps CPU, retries          │
│               (max 3 retries)                   │
│                                                 │
│  OOM KILL   → resource failure                  │
│  (exit=-9)    agent bumps memory, retries       │
│               (max 3 retries)                   │
│                                                 │
│  WRONG OUTPUT → code failure                    │
│  (exit=0 but   call LLM with feedback           │
│  wrong answer) get refined code                 │
│               run again with SAME config        │
│               (max 2 refinement attempts)       │
│                                                 │
│  SUCCESS    → done                              │
│               record final config + reward      │
└────────────────────────────────────────────────┘
        ↓
Compute reward
        ↓
Store transition (s, a, r, s', done)
        ↓
Update policy weights ← THIS IS THE TRAINING STEP
        ↓
Move to next task
```

## Continuous Action Space

### Why not keep the 14 fixed configs

The 14 discrete configs were designed for data collection — they gave good coverage across the resource space. But they are an artificial constraint. In reality a resource allocator can give any amount of CPU and memory. Locking the online agent to the same 14 options means it can never discover that, say, 175 millicores and 110MB is the perfect fit for a particular task type — because that config was never in the original 14.

The continuous action space removes this ceiling.

### How it works

The actor network outputs three numbers between 0 and 1:

```python
state → actor network → [cpu_frac, mem_frac, timeout_frac]

# scale to real values
cpu_mc  = cpu_frac    × 500     # 0 to 500 millicores
mem_mb  = mem_frac    × 256     # 0 to 256 MB
timeout = timeout_frac × 10000  # 0 to 10000 ms

# round to practical granularity before launching VM
cpu_mc  = max(50,  round(cpu_mc  / 50)  * 50)   # nearest 50mc,  min 50
mem_mb  = max(32,  round(mem_mb  / 32)  * 32)   # nearest 32MB,  min 32
timeout = max(1000, round(timeout / 1000) * 1000) # nearest 1s,   min 1s
```

The network learns to output the right fractions for each task type. A complex recursive algorithm gets high cpu_frac and high timeout_frac. A simple string operation gets low everything.

### Why this is a stronger thesis contribution

```
Offline RL  → 14 hand-designed options, static dataset
Online RL   → infinite continuous options, live learning

The online agent can discover resource configs that
the human designer never thought to include.
```

This is the key novelty of the online phase. It is not just online RL — it is online RL with a richer action space that the offline agent could never access.

## Code Refinement Loop

### The problem it solves

28% of transitions in the offline dataset had wrong code — `exit_code=0` but `tests_passed=False`. These are cases where the LLM generated syntactically valid Python that ran fine but produced the wrong answer. The resource config was irrelevant — giving this code more CPU or memory would not help. The code itself was wrong.

In offline RL these transitions were dead weight. The agent could not learn anything useful from them because the failure was not its fault.

### How refinement works

When the online loop detects wrong output it makes one additional LLM call with a feedback prompt:

```python
def build_refinement_prompt(original_code, stdin_data,
                             expected_output, actual_output):
    return f"""You previously wrote this code:

{original_code}

When run with this input:
{stdin_data[:500]}

It produced this output:
{actual_output[:300]}

But the expected output was:
{expected_output[:300]}

Fix the code so it produces the correct output.
Return only the fixed Python code, no explanation, no markdown.
"""
```

The refined code then runs in a new VM with the same config the agent originally chose. If it passes, reward is computed on the refined run. If it still fails, the episode ends with whatever reward the refined run produced.

### When refinement triggers — exact conditions

```python
should_refine = (
    execution["exit_code"] == 0          # code ran
    and tests_passed == False            # but wrong answer
    and not execution["timed_out"]       # not a resource problem
    and refinement_count < 2            # max 2 attempts
    and global_refinements < 150        # session safety cap
)
```

Refinement does NOT trigger on:
- Timeout → RL agent handles this by bumping CPU
- OOM kill → RL agent handles this by bumping memory
- Non-zero exit code with crash → ambiguous, skip refinement
- Already refined twice → stop, avoid infinite loop

### What gets stored

```json
{
  "task_id": "effi_0042",
  "generated_code": "def solve(): ...",
  "llm_output": "938472\n",
  "tests_passed_original": false,
  "refined_code": "def solve(): # fixed ...",
  "refined_llm_output": "291847\n",
  "tests_passed_refined": true,
  "refinement_attempted": true,
  "refinement_attempts": 1
}
```

This lets you analyse post-hoc: what fraction of wrong-code problems were fixed by one refinement? How much did refinement improve overall success rate? These become result tables in your thesis.

## Which RL Algorithm to Use and Why

### The three candidates

**DQN (Deep Q-Network)**
- Designed for discrete action spaces
- Would need to snap continuous outputs back to discrete bins
- The snapping is non-differentiable — gradients do not flow through it correctly
- Not suitable for continuous actions
- Verdict: use for discrete baseline comparison only, not for the main online agent

**TD3 (Twin Delayed Deep Deterministic Policy Gradient)**
- Designed for continuous action spaces
- Deterministic actor — outputs one specific action, no randomness in the policy itself
- Uses two critic networks to reduce overestimation
- Stable and well-understood
- Exploration via adding Gaussian noise to actions: `action = actor(state) + N(0, σ)`
- Verdict: good choice, simpler than SAC, solid baseline for continuous online RL

**SAC (Soft Actor-Critic)**
- Designed for continuous action spaces
- Stochastic actor — outputs a distribution over actions, samples from it
- Has an entropy bonus that encourages exploration automatically
- Does not need manual epsilon or noise tuning
- More sample efficient than TD3 in practice
- More stable training — the entropy term prevents the policy from collapsing early
- Verdict: best choice for your setup

### Why SAC is the right primary algorithm

Your online RL has a specific challenge: 500 problems is a relatively small and diverse task set. The agent needs to explore broadly across task types without collapsing to a single config early in training.

SAC's entropy bonus handles this automatically. The entropy term in the objective function rewards the policy for maintaining uncertainty — it actively prevents the agent from committing too early to one config before it has seen enough examples. This is exactly what you need when you have limited and diverse tasks.

TD3 with fixed Gaussian noise can also work but requires tuning the noise scale manually. If the noise is too small the agent explores too little. If too large it never converges. SAC avoids this entirely.

### Can you use multiple models

Yes, and you should. The thesis comparison becomes:

```

  Shows: does live interaction improve on frozen dataset?
```

### Network architecture for SAC

```python
# Actor: outputs mean and log_std of a Gaussian distribution
class Actor(nn.Module):
    def __init__(self, state_dim=19, action_dim=3):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(state_dim, 256), nn.ReLU(),
            nn.Linear(256, 256),       nn.ReLU(),
        )
        self.mean_head    = nn.Linear(256, action_dim)
        self.log_std_head = nn.Linear(256, action_dim)

    def forward(self, state):
        x       = self.net(state)
        mean    = self.mean_head(x)
        log_std = self.log_std_head(x).clamp(-20, 2)
        std     = log_std.exp()
        dist    = torch.distributions.Normal(mean, std)
        action  = dist.rsample()               # reparameterised sample
        action  = torch.sigmoid(action)        # squash to [0, 1]
        log_prob = dist.log_prob(action).sum(-1)
        return action, log_prob

# Two critics (Twin Q)
class Critic(nn.Module):
    def __init__(self, state_dim=19, action_dim=3):
        super().__init__()
        self.q1 = nn.Sequential(
            nn.Linear(state_dim + action_dim, 256), nn.ReLU(),
            nn.Linear(256, 256),                    nn.ReLU(),
            nn.Linear(256, 1),
        )
        self.q2 = nn.Sequential(
            nn.Linear(state_dim + action_dim, 256), nn.ReLU(),
            nn.Linear(256, 256),                    nn.ReLU(),
            nn.Linear(256, 1),
        )

    def forward(self, state, action):
        x = torch.cat([state, action], dim=1)
        return self.q1(x).squeeze(1), self.q2(x).squeeze(1)
```

### Hyperparameters to use

```python
SAC_CONFIG = {
    "lr_actor":       3e-4,
    "lr_critic":      3e-4,
    "lr_alpha":       3e-4,     # entropy temperature, learned automatically
    "gamma":          0.0,      # single step episodes, no discounting needed
    "tau":            0.005,    # soft target network update
    "batch_size":     256,
    "buffer_size":    10000,
    "warmup_steps":   1000,     # random actions before learning starts
    "update_every":   1,        # update after every episode
    "target_entropy": -3,       # -action_dim as a rule of thumb
}
```

`gamma = 0.0` because your episodes are single step — each VM run is independent, there is no future reward to discount. This simplifies training significantly.

In offline RL you could re-run the prep VM any time because training was separate from collection. In online RL the loop runs continuously — re-running prep VMs mid-training would add 15-30 seconds per task per episode. With 500 problems that is unacceptable.

Everything the online loop needs must be pre-stored and loadable in milliseconds.

## Failure Handling — Exact Logic

### Resource failures (RL agent handles)

```python
def handle_resource_failure(result, current_cpu, current_mem, 
                             current_timeout, retry_count):
    if retry_count >= 3:
        return None   # give up

    if result["timed_out"]:
        # not enough CPU or time — increase both
        new_cpu     = min(current_cpu * 1.5, 500)
        new_timeout = min(current_timeout * 1.5, 10000)
        new_mem     = current_mem   # memory was not the issue
        reason      = "timeout"

    elif result["exit_code"] == -9 and not result["timed_out"]:
        # OOM kill — increase memory
        new_mem     = min(current_mem * 2, 256)
        new_cpu     = current_cpu
        new_timeout = current_timeout
        reason      = "oom"

    else:
        return None   # not a resource failure

    return {
        "cpu_millicores":  round(new_cpu / 50) * 50,
        "memory_limit_mb": round(new_mem / 32) * 32,
        "timeout_ms":      round(new_timeout / 1000) * 1000,
        "reason":          reason,
    }
```

The multiplier approach (×1.5 for CPU/timeout, ×2 for memory) is more natural than stepping through a fixed config list. The agent discovered the initial config — the retry logic respects that by scaling from it rather than jumping to a predetermined next step.

### Code failures (LLM refinement handles)

```python
def handle_wrong_output(task, result, refinement_count, 
                         global_refinements):
    if (result["exit_code"] != 0
            or result["timed_out"]
            or result["tests_passed"] != False
            or refinement_count >= 2
            or global_refinements >= 150):
        return None

    prompt = build_refinement_prompt(
        original_code   = task["use_code"],
        stdin_data      = task["stress_input"],
        expected_output = task["ref_output"],
        actual_output   = result["stdout"],
    )

    refined_code = call_llm(prompt, model="claude-haiku-4-5-20251001")
    return refined_code
```

Always use Haiku for refinement — it is fast and cheap. The refinement prompt is simple enough that it does not need Sonnet.

## The Complete Episode Flow in Code

```python
def run_episode(task, agent, episode_num):
    state      = np.array(list(task["state"].values()), dtype=np.float32)
    code       = task["refined_code"] or task["generated_code"]
    stdin      = task["stress_input"]
    expected   = task["ref_output"]

    # agent picks continuous action
    cpu_raw, mem_raw, timeout_raw = agent.select_action(state)
    cpu_mc  = max(50,   round(cpu_raw  * 500  / 50)   * 50)
    mem_mb  = max(32,   round(mem_raw  * 256  / 32)   * 32)
    timeout = max(1000, round(timeout_raw * 10000 / 1000) * 1000)

    retry_count      = 0
    refinement_count = 0
    retry_history    = []

    while True:
        result = run_microvm(code, stdin, cpu_mc, mem_mb, timeout)
        result["tests_passed"] = (
            result["stdout"].strip() == expected.strip()
            if result["exit_code"] == 0 and not result["timed_out"]
            else None
        )

        # resource failure — RL agent handles
        retry = handle_resource_failure(result, cpu_mc, mem_mb,
                                         timeout, retry_count)
        if retry:
            retry_history.append({
                "cpu": cpu_mc, "mem": mem_mb,
                "timeout": timeout, "reason": retry["reason"]
            })
            cpu_mc  = retry["cpu_millicores"]
            mem_mb  = retry["memory_limit_mb"]
            timeout = retry["timeout_ms"]
            retry_count += 1
            continue

        # code failure — LLM refinement handles
        if result["tests_passed"] == False:
            refined = handle_wrong_output(task, result,
                                          refinement_count,
                                          global_refinements)
            if refined:
                code = refined
                refinement_count += 1
                global_refinements += 1
                continue

        break   # success, or unrecoverable failure

    reward = compute_reward(result, {"cpu_millicores": cpu_mc,
                                      "memory_limit_mb": mem_mb,
                                      "timeout_ms": timeout})

    # update agent
    next_state = build_next_state(state, result)
    agent.update(state,
                 np.array([cpu_raw, mem_raw, timeout_raw]),
                 reward,
                 next_state)

    return reward, result, retry_history
```

```

  python prepare_online_rl.py
  → generates collected/online_rl_inputs.jsonl

WARMUP (first 1000 episodes):

  No gradient updates yet

TRAINING (episodes 1001 onward):
  Agent uses learned policy with entropy exploration
  Updates after every episode
  Saves checkpoint every 500 episodes

EVALUATION (every 200 episodes):
  Run 50 held-out test problems with greedy policy
  (no exploration, just argmax of actor mean)
  Record: avg_reward, success_rate, avg_cpu_used,
          avg_mem_used, refinement_rate
  Plot learning curve
```

## Why This Architecture Is a Strong Thesis Contribution

Three things make this system novel as a research contribution:

**1. Continuous resource allocation learned from live execution**
Prior work on microVM resource allocation uses fixed configs or rule-based heuristics. This system learns a continuous policy from live feedback — the first VM run informs the next.

**2. Separation of resource failure and code failure**
The RL agent handles what it can control (resources). The LLM handles what it can control (correctness). Neither component is asked to solve the other's problem. This is a principled design that generalises beyond this specific system.

**3. Security isolation as a verifiable property**
The microVM layer is not just an implementation detail — it is an empirically verified security boundary. The 40 security probe tasks produce evidence, not just claims.

## Changelog

### 2026-06-12 — Timeout bug fixes, state normalisation, reward floor, cost controls

#### Root cause: integer division sending timeout=0 to guest

`vm.py` was computing `payload["timeout"] = timeout_ms // 1000`. For any
`timeout_ms < 1000` (bins 50, 200, 400, 600, 800ms) this produced `timeout=0`.
Inside `agent.py` the guest cast this with `int(request.get("timeout"))`, so
`subprocess.communicate(timeout=0)` fired immediately, killing the process before
it ran. All sub-1000ms episodes returned `timed_out=True, exit_code=-9`, the
runner retried 3× with the same action, exhausted `MAX_RESOURCE_RETRIES`, and
stored `exit_code=-1`. This looked like VM boot failures but was a pure integer
division bug.

**Fixes applied:**
- `vm.py`: `timeout_ms // 1000` → `timeout_ms / 1000` (float)
- `agent.py` (inside rootfs, written via debugfs): `int(timeout)` → `float(timeout)`
  and `timeout_sec: int` → `timeout_sec: float` in `measure_process`
- `vm_runner.py`: `cpu_limit_sec = max(1, timeout_ms // 1000)` → `timeout_ms / 1000`

After this fix, TIMEOUT_BINS was extended to include 400, 600, 800ms (now valid).
N_TIMEOUT updated to 13.

#### Root cause: unscaled state features biasing untrained actor toward 400ms

Before the StandardScaler is fitted (first 200 episodes), `build_state_vec`
returned raw feature values. `ast_node_count` (~720) and `line_count` (~100) are
orders of magnitude larger than other features and dominated the first Linear layer
of the untrained actor. This consistently pushed the timeout head to index 2 (400ms)
— not random exploration but deterministic bias from large unscaled inputs. Result:
60% of warmup episodes chose 400ms, which (before the division fix) all failed.

**Fix:** added `_RAW_SCALES` to `state_builder.py`. When `scaler is None`, each
feature is divided by its known rough maximum so all inputs arrive in ~[0, 1].

#### VM boot timeout separated from code execution timeout

`AGENT_BOOT_TIMEOUT = 180` was hardcoded in `vm.py` and used for both boot polling
and as a fallback. Refactored:
- `VM_BOOT_TIMEOUT = 30` added to `config.py` — controls `wait_for_agent` polling only
- `send_code` socket timeout is `timeout_ms / 1000 + 10` (was +15)
- VM boot time is completely separate from `action["timeout_ms"]`

#### Reward function floor

`min_viable_tms = wall_ms * 1.5` was teaching the agent that sub-200ms timeouts
were achievable. Python interpreter startup inside the guest takes 50–177ms
(measured empirically), so the true minimum viable timeout is never below ~200ms
even for a trivially fast program. Fixed to:
`min_viable_tms = max(TIMEOUT_STARTUP_OVERHEAD_MS, wall_ms * 2.0)`
where `TIMEOUT_STARTUP_OVERHEAD_MS = 200` lives in `config.py`.

#### API cost controls

Refinement was the primary driver of Claude API spend. Each wrong episode could
trigger up to 2 refinement calls (Sonnet then Opus), neither recorded in
transitions.jsonl. Fixed:
- `MAX_REFINEMENT_ATTEMPTS`: 2 → 1
- Refinement model list: `[SONNET_MODEL, OPUS_MODEL]` → `[SONNET_MODEL]`
  (Opus never used in refinement)
